# 双视频调度卡死问题调查

## 结论

**结论：本案不是 NPU 特有问题。** 在与 NPU 同构的 GPU vLLM `v0.23.0`、Qwen3.5 MTP/EAGLE、
`async_scheduling`、`max_num_batched_tokens=16384` 配置下，两个长视频同样会进入持续的
0-token 调度循环。

**已验证的修复组合：**

1. 回移 `3e6529cc0e` 的 EAGLE 多模态 encoder-cache 生命周期处理；
2. 回移 Qwen3VL 多视频 placeholder 处理的 `d272418f459a` 和 Transformers 5.10+ 兼容
   `dd944845777b`。

其中第 2 项是本次双视频死锁能够恢复的决定性补充：它保留两个视频之间本应存在的
`<|vision_end|><|vision_start|>`，使第一个视频的 cache release 点可达；第 1 项负责在到达
该点后安全释放 cache 并处理 EAGLE 的 +1 look-ahead。

GPU v0.23.0 的端到端验证已经成功：两个视频正常回答，输入 23,337 token、输出 239 token，
HTTP 返回 `200 OK`，请求最终归零。证据日志：
`/root/work/logs/v23/mm-scheduler-trace-mtp-qwen3vl-boundary-fix.log`。

## 证据

### 原始失败：严格相邻 placeholder 导致持续 0-token 循环

GPU v0.23.0 在仅回移 `3e6529cc0e` 时的关键区间为：

```text
video1 [3, 11662)
video2 [11662, 23321)
```

两个视频严格相邻。第一个视频占用 11,520 个 encoder embeds；encoder cache 总预算为 16,384，
因此剩余容量只有 4,864，无法准入第二个视频的 11,520 embeds。

EAGLE 会额外查看一个 look-ahead token。此时调度器状态固定为：

```text
computed_tokens=11661
shift_computed_tokens=1
next_feature_start=11662
encoder_cache_free=4864
encoder_cache_freeable=4864
encoder_embeds=11520
actual_new_tokens=0
```

回退公式为：

```text
11662 - (11661 + 1) = 0
```

因此没有新的 forward，`computed_tokens` 不能增加，第一个视频也不能释放，形成持续循环。旧日志
中 `eagle_mm_boundary_stall` 和 `request_skipped_zero_tokens` 各重复 9,159 次：
`/root/work/logs/v23/mm-scheduler-trace-mtp-v26-backport.log`。

### 修复后：保留视觉边界，单次 stall 后完成 cache 交接

回移 Qwen3VL 多视频处理后，实际 placeholder 区间变为：

```text
video1 [4, 11663)
video2 [11665, 23324)
```

两区间之间存在 2-token gap。这不是填充 token，而是 Transformers 5.14.1 的 Qwen3VL processor
扩展裸 `<|video_pad|>` 时，必须保留的：

```text
<|vision_end|><|vision_start|>
```

本次请求仍短暂出现一次 `encoder_cache_capacity` 和一次 `request_skipped_zero_tokens`，但随即：

```text
computed_tokens=11664
confirmed_tokens=11664
spec_lookahead=1
tokens_until_release=0
release_ready=True
```

第一个视频的 cache reference 被释放，`cache_freeable` 从 4,864 恢复为 16,384；下一轮成功选择
第二个视频。完整统计：

```text
eagle_mm_boundary_stall=1
request_skipped_zero_tokens=1
encoder_feature_selected=2
encoder_cache_reference_released=2
POST /v1/chat/completions 200 OK
Running: 0 reqs, Waiting: 0 reqs
```

## 机制

### 问题触发条件

请求同时满足下列条件时会触发：

- Qwen3.5 MTP，因而 `use_eagle=True`；
- chunked prefill，且总 prompt 超过 `max_num_batched_tokens`；
- 两个视频的 encoder embeds 总量超过 cache budget；
- 旧 Qwen3VL 多视频处理让两个 expanded video placeholder 严格相邻；
- EAGLE 的 +1 look-ahead 首次看到第二个视频时，第二个视频尚无法分配 encoder cache。

### 为什么 `3e6529cc0e` 单独不足

`3e6529cc0e` 修复的是 EAGLE 的 cache 生命周期和 drafter-only cache miss。它确保“到达释放点后”
不会过早释放，也不会把仅被 drafter look-ahead 读到的未缓存 feature 当成 target-model 错误。

但严格相邻时，调度器恰好停在第一个视频释放点之前：

```text
video1 end=11662
computed_tokens=11661
```

没有 forward 就无法到达 release 条件；因此仅有 cache 生命周期修复不能创造前进空间。

### 为什么 Qwen3VL 处理修复有效

`d272418f459a` 将每个视频直接构造成 token replacement，避免逐视频经 HF processor 再序列化时丢失
外围视觉标记。`dd944845777b` 进一步识别 Transformers >= 5.10 的处理器行为：它只扩展裸
`<|video_pad|>`，所以 vLLM 也只能替换裸 video token，不能吞掉外层的
`<|vision_start|>` / `<|vision_end|>`。

这使第一个视频结束后仍有两个正常文本/视觉边界 token，调度器能推进到 cache release 点，随后由
`3e6529cc0e` 交接 cache 给第二个视频。

## NPU 实施方案

修复位于本组织维护的：
`/root/autodl-tmp/coding/ModelArts-Lab/ascend_vllm/patch/platform/`。

| Patch | 上游 vLLM v0.23.0 目标 | 作用 |
| --- | --- | --- |
| `patch_qwen3vl_multivideo.py` | `vllm/model_executor/models/qwen3_vl.py` | 回移 `d272418f459a + dd944845777b`；保留多视频间视觉边界。 |
| `patch_eagle_mm_encoder_cache.py` | `vllm/v1/core/sched/scheduler.py`、`vllm/v1/worker/gpu_model_runner.py` | 回移 `3e6529cc0e` 的 EAGLE cache 生命周期和 drafter-only fallback。 |

这两个 patch 在 `patch/platform/__init__.py` 中自动加载。它们通过 monkey patch 修改已安装的
上游 GPU vLLM `v0.23.0` 类和函数，不修改 `/root/autodl-tmp/coding/vllm-ascend`。

本案实际 NPU 配置为 `DP=1, PP=1, PCP=1, TP=1`。在 `PCP=1` 时，
`vllm-ascend` 的 `NPUModelRunner._gather_mm_embeddings()` 调用上游 `GPUModelRunner`，因此
上述 GPU base-class patch 覆盖当前运行路径。`PCP>1` 的 vllm-ascend 专用 gather 路径未纳入本轮
验证，不能据此宣称已经覆盖。

### 直接替换 vLLM 源码的交付

当前 NPU 实测仍显示严格相邻的 feature ranges，且未观察到 Qwen3VL patch 的对应 trace。因此除
platform monkey patch 外，已整理一份可直接替换 NPU 镜像 `site-packages/vllm/` 的完整回移：

```text
/root/work/handoff/
```

其中的 `replacement/` 提供五个保持原目录结构的完整源码文件；目标镜像没有 Git 元数据，因此不再

## 已淘汰的方案

以下实验性 patch 已删除，不应部署：

- 强推一个 target token 的 EAGLE boundary workaround：不能普适地满足 speculative look-ahead 的
  cache release 条件；
- 强制 `disable_chunked_mm_input=False` 的 patch：没有修复 placeholder 构造和 cache 生命周期；
- 默认注入全量 scheduler trace 的 patch：只用于调查，生产环境会产生过量日志。

### NPU 定向追踪

由于 NPU 环境的实际 runner 和上游 GPU vLLM `v0.23.0` 不完全相同，两个有效 patch 现在都支持
现有开关：

```bash
export VLLM_TRACE_MM_SCHEDULER=1
```

开启后日志以 `MM_PATCH_TRACE` 为前缀。它只增加观测，不改变 scheduler 返回值、encoder cache
分配、placeholder replacement 或模型输出。

| 组件 | 事件 | 用途 |
| --- | --- | --- |
| 两个 patch | `patch_applied` | 证明 NPU 服务进程实际加载了平台 patch。 |
| Qwen3VL | `video_placeholder_ranges` | 输出最终 token-level placeholder 区间、每段长度、替换 target 和相邻 gap；这是验证 NPU processor 是否保留 2-token 视觉边界的直接证据。 |
| EAGLE scheduler | `encoder_schedule_result` | 输出 feature 候选区间、EAGLE shift、encoder budget、已缓存 input、选中的 input 与 cache free/freeable。 |
| EAGLE scheduler | `encoder_schedule_zero_tokens` | 精确标识 0-token 回退时的 `computed_tokens`、下一 feature 起点和 cache 余量。 |
| EAGLE scheduler | `encoder_cache_release_check` / `encoder_cache_reference_released` | 验证第一个视频为何未释放或何时真正变为可回收。 |
| GPU base runner | `gpu_runner_mm_window` | 输出实际执行对象的类名、模块名和 `pcp_size`，确认 NPU 是否进入继承的 GPU gather 路径。 |
| GPU base runner | `gpu_runner_encoder_feature` / `gpu_runner_drafter_only_cache_miss` | 输出 feature cache 命中与纯 drafter look-ahead fallback 是否真实触发。 |

`encoder_schedule_result` 仅在当前窗口包含多模态 feature 或调度结果为 0 token 时输出，避免正常 decode
阶段产生大量无关日志。

NPU 服务重启后，优先验证同一双视频请求，并按以下顺序检查：

```text
1. 两个 patch 都有 MM_PATCH_TRACE ... event='patch_applied'。
2. video_placeholder_ranges 的 adjacent_gaps 包含 2。
3. encoder_schedule_result 中的 runner / cache / feature 边界是否与 GPU 预期一致。
4. 若出现 encoder_schedule_zero_tokens，紧随其后的 release_check 是否为 release_ready=True。
5. gpu_runner_mm_window 的 runner_class 是否为 NPUModelRunner 且 pcp_size=1。
6. 最终是否出现 encoder_cache_reference_released、第二视频被选中和 HTTP 200。
```

若 NPU 在 `PCP=1` 下仍失败，以上事件可区分：patch 未加载、Qwen3VL processor 未形成正确边界、
scheduler/cache 状态仍停在 release 前、NPU runner 未进入 GPU base gather 路径，或存在独立的 NPU
后端问题。

### NPU Qwen3VL patch 定向追踪

NPU 卡死日志中只有 `component=eagle_encoder_cache`、没有
`component=qwen3vl_multivideo`，不能据此断言 Qwen3VL patch 未加载，因为旧 trace 没有覆盖
`_get_prompt_updates()`，且 Qwen3VL processor trace 与 scheduler trace 可能位于不同进程日志。

已确认的调用关系：

- Qwen3.5 虽定义在 `qwen3_5.py`，但注册的是从 `qwen3_vl.py` 导入的同一个
  `Qwen3VLMultiModalProcessor`，因此 patch 目标类正确；
- `vllm.general_plugins` 会在 process0、EngineCore 和 worker 进程执行；
- 多模态 prompt 渲染和 `Qwen3VLMultiModalProcessor` 创建发生在 process0/API renderer；
- `register_kv_failure_patch()` 导入 platform 子模块时会先执行
  `ascend_vllm.patch.platform.__init__`，因此现有入口理论上也会导入 Qwen3VL patch；
- monkey patch 直接替换已 import 的
  `vllm.model_executor.models.qwen3_vl.Qwen3VLMultiModalProcessor` 类方法，对该类已创建的实例同样
  有效。

因此，目前尚未确认的关键点不是“已加载 vLLM 是否可以被 monkey patch”，而是运行时 Qwen3VL
processor 实际选择了哪一种 replacement target。若选择完整视觉三元组，两个视频仍会严格相邻；
若选择裸 `<|video_pad|>`，则会保留其间的
`<|vision_end|><|vision_start|>`。不能在未验证运行时 processor 行为前，强制把所有环境改为裸
token 分支。

Qwen3VL trace 同时扩展为：

- `patch_applied`：输出进程 PID、目标类全名及两个已覆盖方法的模块名；
- `prompt_updates`：输出实际 processor 类、视频数量、video target 和 target mode。

其中 `ProcessorMixin` 仅按上游 `dd944845777b` 的规则检测 processor 的
`replace_video_token` 行为，用来选择裸 `<|video_pad|>` 或完整视觉三元组；它不是 patch 加载的
前置依赖，也不能用当前 shell 的 `pip show transformers` 结果判断 patch 是否生效。后续实验应依据
`prompt_updates` 的实际 `video_target_mode` 和最终 scheduler feature range 判断。

镜像源码一致性只作为兼容性核验，而不是部署方式。当前上游 vLLM `v0.23.0` 参考值为：

```text

qwen3_5.py:  04f3de5372973770d71c5c05f2e8a5e221ec52b62cca7a1e302d9201b61b8adc
```
